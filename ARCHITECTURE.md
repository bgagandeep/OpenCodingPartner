# Architecture

OpenCodingPartner is a chat agent that runs an orchestration agent swarm. You ask that swarm to stand up agents. One turn can stand up a coding agent, a QA agent, a security agent, and a computer agent. Multi-agent is the product.

There is a temporary early-test cap of 8 agents in the code. That cap is for early tests only. It is not a one-worker rule.

## Product path

`ocp chat` is the product. With no message, it is a chat loop. With a message, it runs one turn and exits. `ocp doctor` prints green, yellow, or red for System-1, the meter, orchestration `/healthz`, the write-bridge plugin, Computer capture, Slack, Telegram, and Discord. Discord is yellow because it is not in this build. That line does not post a message and does not print a token. Telegram is green when `TELEGRAM_BOT_TOKEN` and `TELEGRAM_WEBHOOK_SECRET` are set. Computer capture is green when Playwright is installed. That line does not start the browser. Slack is green when `SLACK_BOT_TOKEN` and `SLACK_SIGNING_SECRET` are set. It does not print keys or those values. Yellow means that piece will be an honest skip in the transcript. `ocp doctor --sandbox` also counts pending Approve cards, names each pending card as plan or computer without printing the request, says whether the plan is accepted without printing it, and counts review holds for that sandbox, checks each partner frame that has a page or a frame file, says whether `PARTNER.md` is present, and says whether the last page check passed without printing the page text. It also says who holds the browser and does not take or return it. It says whether a previous run marked the browser live and does not start it. Live stream is not in this build. It reports the last `node --test`, `pnpm test`, or `tsc --noEmit` exit code and does not print the command output. It reports whether the last QA passed and does not print the QA summary. It counts routines and does not run one or print its message. It says whether the last write was orchestration or local and does not print the path. It says which swarm manifest partners are missing and does not apply the manifest or start containers. It does not decide a card, clear a hold, copy the file, start the browser, or print the request text. `ocp prove coding` is a separate scripted turn in a temp sandbox. It uses a local runner, not a live meter. It mkdir, write, glob, patch, copy the patched file to `src/math.copy.mjs`, and `node --test`. The source and the copy match. The transcript says `Copy path: local sandbox.` Exit 0 means the files and the transcript matched. The orchestration gateway does not copy the file in this proof. `ocp prove computer` is a scripted computer chain in a temp sandbox. A fake browser driver opens a page, scrolls, presses Enter, hovers a selector, double-clicks a selector, right-clicks a selector, fills a selector, selects an option by label, checks a box, and checks the page text. Exit 0 means `gtm/last-run.json` recorded a pass and a screenshot for each of those steps. This is one scripted chain, not a full go-to-market run. Orchestration does not run the browser. Playwright is not required.

Each turn does this:

1. The chat agent opens the orchestration session `agent:board:main`.
2. System-1 picks the route. If System-1 is installed, the turn runs `integrations/laya/predict.py` (`Router.predict`) and the transcript says `System-1: real.` If System-1 is absent or the call fails, the fallback router runs and the transcript says `System-1: fallback.`
3. That route becomes one manager plan: session `agent:board:main`, the roles, and the steps. If the orchestration gateway answers `/healthz`, the chat agent sends that plan with `sessions.send`, then calls `tools.invoke` for `skills.status` on that session. The accepted plan is the only standup list. The local swarm does not build a second plan. If the gateway is up but rejects the plan, the turn stops and no worker runs. If the gateway is down, the transcript prints the same plan object with source `local-manager` before workers run. That write is local. The transcript says `Write path: local sandbox.` After the session accepts the plan, this process asks the gateway to invoke `ocp_sandbox_write`, `ocp_sandbox_delete`, `ocp_sandbox_rename`, `ocp_sandbox_mkdir`, `ocp_sandbox_rmdir`, `ocp_sandbox_copy`, `ocp_sandbox_append`, or `ocp_sandbox_todo`. That tool posts to the loopback write bridge in `packages/bundle`. The bridge runs the security gate, then writes the sandbox file. The transcript says `Write path: orchestration.` The plugin the gateway loads is `integrations/openclaw-sandbox-write`. When the gateway answers, `ocp doctor` asks whether `ocp_sandbox_todo` is offered and does not update a list. The gateway still blocks `fs_write`, `apply_patch`, and `sessions_spawn`. This process does not call those tools. If `ocp_sandbox_write` is not installed, the turn falls back to the built-in `write` tool with an absolute sandbox path. If that refuses, the file does not land. A general edit is drafted in a temp directory by the meter, then each file goes through the same bridge. The meter order stays proxy, then compatible, then the coding worker.
4. The swarm stands up only the roles in that plan.
5. The security agent checks the path and the contents before a write.
6. The coding agent edits the sandbox. A general request is the prompt, with the sandbox as the working directory. The prompt also lists text files already in the sandbox, skipping secrets, so a follow-up turn is not blind. The same prompt starts with `Prior turns:` for this session and this sandbox only: up to six short lines, about 4k characters, with the user text and whether QA passed. Blocked secrets are not copied into that history. The lines are also written to `.ocp/prior-turns.json` in that sandbox and read back when the process starts again. Listing and grep skip `.ocp/`. One turn can list, grep, glob a relative pattern such as `src/**/*.ts` or `*.md`, read, patch, write, delete one file, rename one file, copy one file (through `ocp_sandbox_copy` when the gateway drove the turn, otherwise locally; a missing plugin falls back locally; a refusal does not copy locally). Append adds text to one existing relative file and does not create a file (through `ocp_sandbox_append` when the gateway drove the turn, otherwise locally; a missing plugin falls back locally; a refusal does not append locally). A missing file, a directory, `../`, a secret, `gtm/`, or `.ocp/` is refused. The transcript says `Append path: orchestration.` or `Append path: local sandbox.` The turn can also mkdir one directory and run `node --test`, `pnpm test`, or `tsc --noEmit`, plus read-only `git status` (no args, `-sb`, or `--short --branch`) and `git diff` with relative paths, and `git log --oneline -n N` with N from 1 to 20, and `git show HEAD:` plus one relative path, then feed those results back for another round in the same turn. Delete unlinks a single file after the security gate. It does not remove directories or `gtm/` evidence. When the gateway drove the turn, it invokes `ocp_sandbox_delete` or `ocp_sandbox_rename` on the same bridge. The transcript says `Delete path: orchestration.` or `Rename path: orchestration.` If that plugin tool is missing, the step runs in the local sandbox and the transcript says so. Rename moves one file to another relative path in the same sandbox and does not overwrite. Mkdir creates one relative directory and its parents. An existing directory is a no-op. A file, `../`, an absolute path, `gtm/`, `.ocp/`, or a secret path is refused. When the gateway did not drive the turn, the transcript says `Mkdir path: local sandbox.` When it did, mkdir uses `ocp_sandbox_mkdir` and the transcript says `Mkdir path: orchestration.` A missing plugin falls back to the local sandbox. Rmdir removes one empty relative directory. A file or a non-empty directory is refused. When the gateway did not drive the turn, the transcript says `Rmdir path: local sandbox.` When it did, rmdir uses `ocp_sandbox_rmdir` and the transcript says `Rmdir path: orchestration.` A missing plugin falls back to the local sandbox. A refusal does not remove the directory locally. The same turn can add or complete a local todo. The list holds at most 12 items in `.ocp/todos.json`. Secret text and `../` are refused and not stored. `ocp todo list` shows the session and partner lists and does not change them. `ocp todo add --text` and `ocp todo complete --text` change that same checklist for the session or `--partner`. A secret is refused and is not stored. `ocp doctor` counts open items and does not print the text. When the gateway drives the turn, the list is updated through `ocp_sandbox_todo`. A missing plugin updates it locally. A refusal does not update it locally. The transcript says `Todo path: orchestration.` or `Todo path: local sandbox.` Grep is an in-process substring or `/pattern/` search. It skips secrets, binaries, and `gtm/`. The cap is ten rounds. It stops on no more steps, a passing check, or an explicit done. A failed check is still retried up to two times with the command output in the prompt. The meter is chosen in this order: a proxy key (`LITELLM_API_KEY` or `LITELLM_MASTER_KEY`, base `LITELLM_BASE_URL` or `http://127.0.0.1:4000/v1`), then `OPENAI_API_KEY` plus `OPENAI_BASE_URL`, then the native coding worker (`XAI_API_KEY` and `grok -p ... --cwd ... --output-format streaming-json`). The proxy sits behind the same coding worker. It is not a required peer of the gateway. The transcript says which meter ran. When the sandbox has `PARTNER.md`, an open edit writes intent, spec, and plan under `.ocp/sdlc/` and an Approve card at `.ocp/approvals.json`. The coding worker does not edit until you say `approve` or `accept the plan`. `deny` and `redirect:` decide that card. After the edit, the coding worker runs `node --test` in the sandbox and the transcript reports the exit code. QA does the mechanical review. The Approve card is the human intent and risk decision. A failed check returns to intent. While `.ocp/sdlc/review-hold` exists, orchestration stands up one coding worker. `ocp approve accept` accepts that plan again and clears the hold. It does not replace the intent. The board session already runs one turn at a time. `PARTNER.rules` and `.ocp/rules` load into the coding worker prompt. A `block:` line stops a matching request. A partner turn also loads those files from the read-only shared session and does not copy them. `ocp computer` is the Computer tab for the sandbox desktop. It shows status and the last frame path. There is no live pixel stream in this build. `takeover` and `return` hand the browser between you and the partner. With `PARTNER.md` present, computer-use waits on an Approve card before the partner opens a page. A turn with a partner id uses `.ocp/fleet/<id>` as its workspace and its Computer tab. The session root is recorded as a read-only `/shared` mount. A partner list, read, grep, or glob of `shared` or `shared/path` uses that root and does not copy it. A write to `shared` is refused. `ocp fleet status` lists partners, container state, and the last frame. It does not start containers. No telemetry is sent. `ocp fleet start` runs the container when Docker answers. If Docker is missing, the command fails and the Computer tab stays not started. `ocp computer capture` writes `gtm/last-frame.png` after a page is open. After computer-execute, capture copies the step screenshot to that file and Computer QA `computer-frame` checks it. A missing page, a missing screenshot, or a file that is not a PNG fails the turn in the transcript. With a partner id, the frame stays in `.ocp/fleet/<id>/gtm/`. A missing browser does not write a blank image. A live pixel stream, a fleet grid, and telemetry are later. Routines live in `.ocp/routines.json`. An interval routine that is due, or a named event, runs as a partner turn. Slack and Telegram inbound text uses that same turn, including approve and deny. Slack posts a reply when `SLACK_BOT_TOKEN` and `SLACK_SIGNING_SECRET` are set. Inbound Slack events are checked with that signing secret. Without them the offline turn still runs. Telegram posts a reply when `TELEGRAM_BOT_TOKEN` and `TELEGRAM_WEBHOOK_SECRET` are set. Inbound Telegram updates are checked with that webhook secret. Without them the offline turn still runs. WhatsApp is later. `ocp swarm apply` reads a JSON manifest and creates `.ocp/fleet/<id>` for each partner, plus any routines in that file. `--dry-run` writes nothing. The manifest does not start containers. A fleet grid and telemetry are later. Advanced ACP is an opt-in switch, off by default. Turning it on does not replace orchestration. No backend is installed. Packaging in Settings is a free OSS core. Seats and credits are design only. Billing is inert. No payment provider is connected. The QA agent reviews the files that changed. The security agent checks the request before the edit and the written files after it. Without a key, a simple create-file message still uses the local sandbox worker. Any other request is refused. The offline path is not a stand-in for a live model.7. The computer agent writes a go-to-market plan. Actions stay `executed: false` unless you pass `--computer-execute` or set `OCP_COMPUTER_EXECUTE=1` and name an http or https URL. Then this process opens that URL, reads the title and page text, and types into a CSS selector when the message says `type "text" into SELECTOR`. Playwright (headless Chromium) does that work here. `gtm/last-run.json` lists each step, and each finished step saves a screenshot under `gtm/`. A step is `executed: true` only if it ran. The message can chain `expect title`, `expect text`, `type ... into`, `click`, `navigate` to another URL on that same host, `wait SELECTOR` or a short `wait Nms` capped at 30 seconds, `scroll down`, `scroll up`, `scroll N` capped at 2000 pixels, or `scroll SELECTOR` to bring that element into view, `press KEY` for Enter, Escape, Tab, Backspace, or an arrow key, and `expect selector ... value`. Any other key fails. `hover SELECTOR` or `hover "text"` moves the pointer onto that element. `double-click SELECTOR` or `double-click "text"` clicks that element twice. `right-click SELECTOR` or `right-click "text"` clicks it with the right button. `fill SELECTOR with "text"` or `fill "label" with "text"` clears that field and types the quoted text. `select SELECTOR option "label"` or `select "field" option "label"` chooses that option by its visible label. `check SELECTOR` or `check "label"` checks that box. `uncheck SELECTOR` or `uncheck "label"` clears it. A missing selector, quoted target, or option fails that step. Each finished step records pass or fail in `gtm/last-run.json` and saves a screenshot. A failed step stops the chain. Later steps stay `executed: false`. The QA agent checks `gtm/assertion.json` and, after a coding write, any `expect file path to contain "..."` clause. A missing snippet, an empty file, or a file removed by security fails that review. A failed file or page check is retried up to two times. Each file retry uses the same write path as the first write. If QA still fails, the transcript says the fix budget is exhausted. The orchestration gateway does not run the browser and does not write those files.

The transcript is one block: session, route, which System-1 path ran, the manager plan, which agents stood up, the security decision, the file write, the QA result, and the computer plan.

## A turn

1. You send a message to the chat agent (`ocp` or `opencodingpartner`).
2. The orchestration agent swarm opens a session. The session shape is a binding of channel, account, and agent, and a session key like `agent:board:main`.
3. System-1 picks the route and does not write code. The real bridge is `integrations/laya/predict.py`. The chat turn runs it when `pnpm bundle:install` has created `.bundle/laya`, with `HF_HOME` pointed at `.bundle/laya/hf`. Otherwise the transcript says the fallback ran. The offline demo does not download weights.
4. The swarm stands up the agents the route needs. A build-and-sell request stands up all four roles.
5. The security agent checks the path and the file contents before any write. It blocks path escape and secrets.
6. The coding agent writes files. Offline, a local sandbox worker does the write. The coding worker seam builds `grok -p "<prompt>" --cwd <dir> --output-format streaming-json` and calls an injected runner. The demo does not spawn `grok`.
7. The QA agent checks the file that was written.
8. The computer agent records a go-to-market action plan. With live execution off, no browser runs and each action is `executed: false`. With live execution on, Playwright opens the named URL, reads the screen, and types into one selector when you ask.

Turns on the same session run one after another. The same message on the same sandbox replays the stored result.

## Which tool runs what

| User-facing name | Runs on |
| --- | --- |
| Chat agent / chat bot | OpenCodingPartner CLI + orchestration |
| Orchestration agent swarm | Orchestration gateway. The pin and license are in THIRD_PARTY_NOTICES.md. We do not vendor this code. |
| Coding agents + QA agents | Coding worker. The pin and license are in THIRD_PARTY_NOTICES.md. We do not vendor this code. |
| Computer agents (GTM) | Computer-use worker seam. Offline, it only records the plan. With `--computer-execute`, Playwright opens the named URL, reads the screen, and can type into one selector from this process. |
| Security agents | Policy/security worker seam. It runs in the coding path, before the write. |

System-1 only picks the route. The package pin and the English checkpoint are in THIRD_PARTY_NOTICES.md. `pnpm bundle:install` downloads about 800 MB into `.bundle/laya/hf`. That directory is not committed. The call shape is `router.predict(state, questions, model="english")`. Question types are choice, score, and noul.

## Packaging

```text
pnpm bundle:install
        |
        +-- .bundle/openclaw   npm openclaw@2026.9.6          orchestration agent swarm
        +-- .bundle/grok       npm @xai-official/grok@1.0.41   coding agents and QA agents
        +-- .bundle/laya       pip laya==0.3.13               System-1 bridge
        +-- docker compose     ghcr.io/openclaw/openclaw:2026.9.6
```

The chat agent reads `.bundle/stack.json` or `OCP_OPENCLAW_BIN`, `OCP_GROK_BIN`, and `OCP_LAYA_PYTHON`.

`pnpm demo:connected` (`ocp demo --live`) does two real steps:

1. It checks `GET /healthz` on the orchestration gateway (`http://127.0.0.1:18789`, or `OPENCLAW_GATEWAY_URL`). If the gateway answers, the chat agent sends a turn with `openclaw gateway call sessions.send` on session `agent:board:main`. If the `openclaw` binary is missing but HTTP is up, it uses `POST /v1/chat/completions`. If nothing answers `/healthz`, the chat turn is skipped.
2. Coding and QA agents call the bundled `grok` binary through the coding worker (`grok -p ... --cwd ... --output-format streaming-json`) when `XAI_API_KEY` is set. `OPENAI_API_KEY` plus `OPENAI_BASE_URL` selects the compatible meter instead. The key stays in the operator environment. This repo does not store it. If no key is set, that step is skipped.

The report says what ran and what was skipped. The offline sandbox demo does not use this path. Optional gateway auth is `OPENCLAW_GATEWAY_TOKEN`. Do not put that token in the repo.

## Independence

`pnpm bundle:install` fetches the pinned packages into `.bundle/` and downloads the System-1 English weights there. This repo does not commit their source or their weights. Orchestration owns the session plan. A create-file after that plan uses the gateway `write` tool. General model edits still run in this process. We are not affiliated with those projects.
